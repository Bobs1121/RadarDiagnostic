# Gen6 AI：持续开发执行规范

状态：当前唯一开发执行规则；配合 [Sprint](GEN6_AI_SPRINT_PLAN.md)、[验收](GEN6_AI_ACCEPTANCE.md)、[模块](GEN6_AI_MODULE_DESIGN.md)。产品需求仍由产品基线定义。

## 1. 目标模式的用途与边界

持续目标用于按验收证据推进产品，不是无限循环增加功能。任务预算、模型配额、宿主是否运行和权限仍会限制执行；本文件不承诺无限后台工作。Codex 的长期目标概念参考 [官方 Follow a goal](https://learn.chatgpt.com/use-cases/follow-goals)。本文主要定义项目内的可恢复工作纪律，不依赖特定 `/goal` 参数语法。

本轮仅准备文档和控制资产，没有启动产品开发 goal，也没有授权远端编译、GDB、算法仓写入或发布。

## 2. 状态的唯一来源

| 信息 | 维护位置 |
|---|---|
| 产品/设计事实 | 本套 DDD 文档；用户新需求先记录，再同步受影响设计 |
| 待做任务、依赖、当前切片、阻塞与下一步 | `gen6_execution_state.v1.json` |
| G6-AC 发布状态、实际测试层级与证据 | `release_acceptance.v1.json`；状态语义沿用现有 gate |
| 最新接续摘要 | `GEN6_AI_HANDOFF.md`，引用状态与证据，不复制另一套状态表 |
| 运行结果 | `evidence/` 或明确登记的报告路径；带 hash/身份，不提交 GB 数据 |
| 旧设计/旧验收 | `docs/archive/2026-09-17/`；只作历史线索，非当前指令 |

开发状态与产品 AnalysisRun 不同：前者记录建产品，后者记录产品分析雷达案例，禁止复用为平行产品状态树。

## 3. 每轮执行循环

1. **恢复**：读取索引、执行状态、handoff、当前 Sprint 和任务关联设计；检查实际 cwd/分支/HEAD/dirty、活跃本地/远端进程及授权。旧摘要与当前文件不一致时先核对事实。
2. **选择**：优先修复阻塞主链路的准确性/权限/数据损坏问题，其次完成当前纵向切片，再做依赖已满足的下一任务；不只挑容易变绿的外围模块。
3. **准备**：写清任务卡的需求/AC、前后用户行为、所有生产者/消费者、接口差异、非目标、验证与回退。缺少设计事实自行读代码；业务方向/关键输入不明立即问。
4. **实现**：最小完整改动，复用已有模块；不只实现 producer 就宣布能力完成。每次仅一个主集成切片处于 in_progress。
5. **验证**：针对风险运行相关单元/契约→边界联调→真实用户入口/页面/回放（授权范围内）。失败定位原因修复后重跑，不改期望值或跳过测试来消除红灯。
6. **评审**：按第 6 节独立视角审查证据、体验、耦合和范围；可自己完成，不要求自动启用子代理。
7. **落盘**：更新任务状态、AC 层级证据、接口/AGENTS、handoff；检查 final diff 与本轮文件所有权。可安全提交本轮局部变更时按 Git 规则 checkpoint。
8. **继续**：还有已授权且依赖满足的任务就继续；不能仅因一个 Sprint 或本地测试通过而结束总体目标。

开始时执行 `python tools/check_ddd.py` 检查文档/任务依赖；文档检查通过只表示结构一致，不是产品通过。

## 4. 任务状态和完成定义

任务状态：`todo → in_progress → verifying → done`，可进入 `blocked`。blocked 记录真实原因、已尝试方法、需要何种外部变化、替代工作；解除后回到 todo/in_progress，不直接 done。

`implemented` 不等于 `done`。任务 done 要求所分配层级验证完成、集成消费者可用、相关文档一致、证据存在、没有掩盖的影响当前切片的阻塞。局部任务 done 不自动将其关联 AC 标 accepted。

AC 沿用 `specified / implemented / partially-verified / accepted / blocked / deferred`。首期 required AC 不得由 AI 自行设为 optional/deferred，也不得降低验收层级。远端/浏览器证据不足只可 partially-verified，不用 mock 补成真实验收。

## 5. 模块耦合与变更门

| 边界 | 同步生产/消费方 | 必须联调 |
|---|---|---|
| 输入/身份/新鲜度 | M01→M02/M03/M04/M07/M11 | 分支/COEM/dirty 改变后缓存和执行失效，静态可用部分仍可继续 |
| 事件/帧/目标 | M02→M03/M08/M10 | 多雷达同 ID、时间映射、无报警窗口、视频关联 |
| 工具目录与调用 | M04 registry→生成 TS→bridge→module/provider | 实际 Pi 工具选择和参数到达；不只测试 Python 函数 |
| 计划/授权/执行 | M05/M06→M07/M08/M09 | 同意后执行、重连防重、拒绝扩大范围、取消与清理 |
| 运行态/条件/结论 | M08→M03/M04/M05/M10 | unknown/optimized_out/unbound 不升级 observed，作用域和阶段正确 |
| 页面动作/修订 | M10→M05/M04/M06→M10 | 点击/追问→权威状态→增量呈现，刷新/重复点击/旧 revision |
| 修改/验证 | M09→M07/M08/M10 | 同输入基线/修改版比较、构建失败、恢复原版 |
| 用户反馈/知识 | M05→M11→M04 | 用户判断不成为 runtime，过期/跨项目知识不能进入 prompt |
| 安装/升级 | M12→所有模块 | 干净环境入口、schema 兼容、旧案件可读、配置不丢 |

接口变更在任务卡列出字段、兼容性、所有调用者、测试和迁移。先定义契约 fixture 和错误语义，再实现双方；单侧完成时 task 继续 verifying。新增依赖需说明维护/安装/性能成本，不能为便利引入第二个调度器或平行数据模型。

## 6. 自我纠偏与回顾

每轮检查：是否更接近用户可用流程；是否让用户手工补技术信息；是否只加工具/manifest；是否用条件计数替代 AI 推理；是否用猜测补证据；是否与当前 source/data/config 对齐；是否破坏隔离或授权。

出现以下情况立即回顾当前路线：同类失败两次仍无新信息；连续两个切片无用户可见进展；新增状态/schema 与现有职责重复；测试越来越多但真实入口仍不可用；关键性能成本增加；实现发现设计前提不成立。

回顾输出：观测→根因假设→最小可验证调整→受影响文档/任务→结果。实现方法可自行调整；产品范围、验收阈值、授权和外部副作用改变必须问用户。不能把目标改小来宣称达成，也不能以“重构更优雅”为理由无限延迟用户闭环。

## 7. 测试与交互验证纪律

每次改动先跑受影响测试；涉及 shared schema/bridge/config/ledger 时覆盖所有相关消费者。Sprint 出口跑影响域回归及真实入口；发布跑完整适用套件。通过后仅在新增变更/失败/未解风险时重复，不无意义循环全量测试。

UI 变更必须用真实浏览器操作验证选择、加载、空/错误/partial、窄屏、键盘、刷新/重连；截图仅证明呈现，不能替代动作状态验证。无可用浏览器环境则该层待验证。算法仿真、Pi-product、人工业务裁决分别记录，不混写“全部通过”。

记录命令/返回码/输入/版本/产物，失败原文保留。禁止只维护“测试数增长”，禁止削弱 assert、扩大 allowlist、新增 skip/xfail 以过关；确属过期测试需说明旧契约为何被用户确认的新契约替代并增加等价覆盖。

## 8. Git 与工作区规则

- 先确认仓库 root、分支、HEAD、staged/unstaged/untracked 清单。当前大量既有 dirty 修改不能被 AI 自动当成本轮成果。
- 默认在当前工作区推进最小授权任务；需要隔离分支/worktree 时由实际基线创建。普通 HEAD worktree 不含 dirty 修改，不能假装包含；必须明确纳入哪些差异并校验，不自动 stash/reset/clean。
- 可以为后续已授权本地开发建立自己的分支和小范围本地 commit；先 review diff，逐路径/逐 hunk stage，检查 staged diff，不用 `git add .` 混入用户修改。文件含交错未知改动且无法安全分离时保留未提交并提问。
- 本轮归档整理不自动提交先前全部工作区。后续任务记录本地 commit 或未提交 patch 的 hash/路径，保持可恢复，不强迫每轮一定 commit。
- commit 建议 `feat|fix|test|docs(scope): ...`，正文含任务 ID/AC、用户行为和验证。一个 commit 代表可审阅切片，不能只有“大量改进”。
- push、merge、force push、历史重写、大范围删除、他人分支改动须显式确认；无授权时本地准备到可 review 状态。
- 不自动拉取/切换作为调查对象的算法仓，版本准备属于独立执行授权。冲突保留双方意图，无法判断所有权立即问。
- 回退自己的独立 commit 可准备 revert；dirty 工作区先比对外部变化，禁止全仓 reset。不得提交 secrets、原始 bag、构建 binary、大型缓存。

## 9. Handoff 与压缩恢复

每个切片结束、被打断前、Sprint 出口更新 `GEN6_AI_HANDOFF.md`；缺少完成证据不能写“可直接进入下一 Sprint”。格式与当前基线见该文件。handoff 指向状态，不成为新的需求入口。

新会话先核查 handoff 的 HEAD/dirty/产物/进程是否仍存在；失配先 reconcile。报告“上轮通过”不能替代当前变更后的相关回归。长期日志可以放 evidence，保持最新 handoff 简短。

## 10. 阻塞与整体停止条件

单项受阻时继续不依赖该条件的任务，同时立即提出必要问题。依赖未满足的任务不能假装 done，也不能无限扫描或重复失败。当前 goal 的 blocked/complete 状态严格按宿主工具规则使用，本文件不覆盖宿主规则。

只有全部首期 required AC 在所需层级真实通过、跨模块/UX/部署/性能验收完成、没有未解决关键缺陷、状态与证据一致且最终 diff 已审阅，才可宣告总体目标完成。预算耗尽、用户暂停、等待授权或测试机器不可用都不是完成。

## 11. 可用于后续 goal 的启动文本

以下是目标内容，不是要求当前会话执行它，也不臆造 `/goal` 的命令参数：

```text

先读取 gen6_execution_state.v1.json、GEN6_AI_HANDOFF.md 和 GEN6_AI_SPRINT_PLAN.md，核验实际 Git/dirty 状态，从依赖满足且最能推进用户闭环的任务开始。执行“设计核对→实现→相关回归→跨模块/浏览器/Pi/真实仿真验收→评审→更新状态与 handoff→下一任务”，不要仅完成计划或一个模块就停止。
本地搜索、修改、构建、测试和本轮自有变更的小范围本地 commit 可自主进行；保护既有 dirty 修改。push/merge、历史重写、删除、凭据权限修改、外部写入以及实际远端编译/回放/GDB/算法仓修改，按现有授权范围执行，缺授权时先准备具体计划再问，不自行扩大权限。
有业务歧义或方向冲突立即问我，同时继续独立工作。真实条件不足时保留 partial/blocked，不能用 mock、跳过测试、降低目标或改验收标准声称完成。每个切片更新事实和恢复入口；首期全部验收满足才结束总体目标。
```
