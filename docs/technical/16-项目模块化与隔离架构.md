# 项目模块化与隔离架构设计 (Project-Centric Modular Architecture)

## 1. 核心设计理念

系统的演进目标是打造一个**“乐高式的高内聚积木” + “强隔离的多租户工作区”**的架构。
这就要求系统必须在两个维度上进行彻底的解耦：
1. **横向（功能维度）**：各个能力模块必须是独立的库，可单点调用，也可组合进复杂管线。
2. **纵向（业务/项目维度）**：所有的状态、记忆、规则、配置必须归属到明确的“项目工作区（Project Workspace）”，AI 的推理上下文必须在项目之间做到 100% 物理隔离。

---

## 2. 横向：功能模块的“积木化” (Composability)

系统中的核心能力将被拆解为独立的微内核，它们有自己明确的输入和输出，不再强依赖于全量级 `Orchestrator`。

| 模块名称 (Module) | 独立运行场景 (Standalone Use Case) | 组合运行场景 (Composed Use Case) |
| :--- | :--- | :--- |
| **DataProbe / SignalPlotter** | 客户给了一份数据，工程师只需敲入 `python tools/plot_signals.py`，就能把指定功能的关键信号抽出来看波形。 | 作为诊断管线中的“取证”环节，为大模型提取 TPE 时序模式提供底层数据。 |
| **CodeGraph (AST Parser)** | 工程师想知道“到底有几个地方改了 `FCTA_Warn`”，直接通过 AST Query 查询，生成依赖树。 | 作为诊断的“静态分析”环节，辅助 LLM 定位出 Bug 发生的精确行号。 |
| **Harness (评估器)** | 快速对今天系统生成的批量报告打分，评估可用性。 | CI/CD 流程中，自动对修复建议的正确性进行回归测试。 |
| **Memory Auto-Dream** | 离线静默运行，让系统自己学习新接手代码的业务逻辑。 | 在每次诊断完成后，把成功的排查经验自动沉淀到项目知识库中。 |

---

## 3. 纵向：项目环境的“强隔离” (Project Isolation)

为了满足“不同项目的代码流程、需求、数据都不一样”，我们将重构当前的目录规范，引入 **`Workspaces` (工作区)** 概念。

### 3.1 工作区目录结构规范设计
摒弃将 `memory`、`source_docs`、`golden_truths` 散落在全局不同文件夹的做法，将一个项目的所有资产全部收拢到其独立的工作区中。

```text
radarAnalyze/
├── workspaces/                      <-- 新增：所有项目的资产总集
│   ├── gen6_gwm_b26/                <-- 独立项目A (长城 B26)
│   │   ├── config.yaml              <-- 该项目特有的管线配置、参数阈值
│   │   ├── requirements/            <-- 该项目的需求文档 (如 FCTA 必须 2s 触发)
│   │   ├── dbc/                     <-- 该项目专用的 DBC 矩阵
│   │   ├── memory/                  <-- 该项目积累的记忆
│   │   │   ├── codegraph.db         <-- 专属于该项目的代码 AST 图谱
│   │   │   ├── constants.json       <-- 该项目学习到的数值常量
│   │   │   └── sessions/            <-- 历史诊断经验沉淀
│   │   └── source_docs/             <-- 该项目源码生成的宏观说明
│   │
│   └── gen5_byd_seal/               <-- 独立项目B (比亚迪海豹)
│       ├── config.yaml
│       ├── requirements/
│       ├── dbc/
│       └── memory/                  <-- 完全隔离的代码图谱和经验池
│
├── ai/                              <-- 纯净的算法与逻辑层 (无状态)
├── parsers/                         <-- 纯净的数据解析器
└── cli.py                           <-- 统一入口，通过 --workspace 指定上下文
```

### 3.2 项目级配置化流程 (Configurable Pipeline)
因为不同项目对诊断的流程和侧重点不同，`Orchestrator` 将不再写死流程，而是由 `workspaces/<project>/config.yaml` 驱动：
- 某些低配雷达项目，不需要跑全量 5 个专家，配置里可以定义 `expert_panel: light`。
- 某些项目数据格式为特殊的自研协议，可以挂载该项目专用的 parser 插件。
- 每个项目的“需求 (Requirements)”独立，AI 诊断时只会读取当前工作区下的需求设定作为金标准（Ground Truth）。

## 4. 演进路线建议

1. **第一步：物理隔离迁移**。创建一个脚手架脚本，把现有分散的 `memory/projects/gwm_b26`、`source_docs/gwm_b26`、`cases/golden_truths` 统一搬迁合并到 `workspaces/gen6_gwm_b26/` 结构下。
2. **第二步：配置下放**。让 AI 引擎启动时，首先加载全局模型配置，然后叠加上 `workspaces/<project>/config.yaml` 的项目特有规则。
3. **第三步：需求注入**。在诊断 Prompt 组装时，动态读取该工作区的 `requirements/*.md`（比如项目特有的报警时序要求），使得 AI 的诊断结论完全贴合该主机厂的验收标准。
