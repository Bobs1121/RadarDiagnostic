## 二、当前管线各阶段鲁棒性评估

| 阶段 | 鲁棒性 | 风险 | 说明 |
|------|--------|------|------|
| **数据解析 (BAG)** | ⚠️ 中等 | BAG 格式固定，但 ROS topic 命名可能变化 | 硬编码 topic 路径 (`/wf/corner_radar/lgu_data_1`) |
| **数据解析 (BLF)** | ✅ 高 | cantools 成熟，DBC 解码稳定 | 依赖 DBC 文件正确性 |
| **数据解析 (MF4)** | ❌ 无 | 尚未实现 | **核心缺失** |
| **时间同步** | ✅ 高 | 基于时间范围对齐，容错好 | BAG/BLF 时间差自动计算 |
| **测试窗口检测** | ⚠️ 中等 | 速度阈值硬编码 | 不同场景可能需要不同阈值 |
| **帧级证据提取** | ✅ 高 | 基于 SQL 聚合，稳定 | 窗口感知，只分析有效数据 |
| **条件提取** | ⚠️ 中等 | LLM 依赖，可能遗漏条件 | CodeGraph 增强后提升 |
| **TPE 时序模式** | ✅ 高 | 确定性模式匹配 + 数据对齐 | 不依赖 LLM |
| **变量探测** | ⚠️ 中等 | LLM 规划 + SQL 执行 | 可能提出无效查询 |
| **抑制信号检查** | ⚠️ 中等 | 依赖 signal_mapping 完整性 | 映射不完整时无法检查 |
| **专家面板** | ⚠️ 中等 | LLM 主导，prompt 质量决定一切 | 60K 字 budget 可能截断关键信息 |
| **报告生成** | ✅ 高 | HTML 模板 + Plotly | 稳定 |

**整体鲁棒性评分**: 6.5/10

**关键脆弱点**:
1. **LLM 依赖链过长**: 问题理解 → 条件提取 → 变量探测 → 专家面板，5 个 LLM 调用串联，任一失败影响下游
2. **ContextBudget 截断**: 60K 字 budget，当数据量大时可能截断关键证据
3. **信号映射不完整**: signal_mapper 只能识别 RteComMapping.c 中的模式，rteLite_PriCan.h 的 240 个信号只有节点没有边
4. **BAG topic 硬编码**: topic 路径写死，其他车型/传感器需要改代码
5. **MF4 不支持**: 大量测量数据无法使用

## 三、目标差距分析

### 差距 1: MF4 数据输入 (❌ 完全缺失)

**现状**: 不支持 MF4 格式。

**影响**: 用户使用 CANoe/Canalyzer 导出的测量数据无法直接使用。

**修复方案**: 新增 `parsers/mf4_parser.py`，复用 FrameStore 写入接口。

**工作量**: 中等 (2-3 天)

### 差距 2: 代码修改方案 (⚠️ 仅有文字建议)

**现状**: expert_panel 输出"修复建议"是文字描述，如 "将阈值从 5 降至 3"。

**影响**: 用户需要自己找到代码、修改代码、验证效果。工具没有完成最后一公里。

**修复方案**: 
1. 新增 `ai/codefix_engine.py`
2. 使用 CodeGraph 精确定位代码位置
3. 调用 coder LLM 生成 unified diff
4. embedded-c-runtime-safety 安全审查

**工作量**: 中等 (3-4 天)

### 差距 3: 修改效果预估 (⚠️ 仅 tune/verify 模式支持参数级)

**现状**: `parameter_analyzer.what_if` 仅支持参数调整的效果模拟。

**影响**: 代码逻辑修改的效果无法预评估。

**修复方案**: 扩展现有 `what_if` 引擎，支持条件判断逻辑的模拟。

**工作量**: 小 (1-2 天)

### 差距 4: 交互式追问 (❌ 完全缺失)

**现状**: 一次性诊断，不支持追问。

**影响**: 用户无法对诊断结果进行深入讨论。

**修复方案**: 基于现有 `query` 模式扩展交互模式。

**工作量**: 小 (1-2 天)

## 四、架构能否实现用户需求的评估

### 用户需求: "输入数据 + 提问 → 诊断根因 + 给出修改源码方案"

| 需求子项 | 能否实现 | 当前状态 | 需要做什么 |
|----------|----------|----------|-----------|
| 输入 BAG 数据 | ✅ 能 | 已实现 | 无需改动 |
| 输入 BLF 数据 | ✅ 能 | 已实现 | 无需改动 |
| 输入 MF4 数据 | ❌ 不能 | 未实现 | 新增 Mf4Parser |
| 用户提问 | ✅ 能 | 已实现 (problem + expected) | 无需改动 |
| 解析回放数据 | ✅ 能 | 已实现 (FrameStore) | 无需改动 |
| 诊断问题原因 | ✅ 能 | 已实现 (专家面板) | 提升鲁棒性 |
| 给出修改源码方案 | ⚠️ 部分能 | 仅有文字建议 | 新增 CodeFixEngine |
| 可执行的 diff | ❌ 不能 | 未实现 | 新增 CodeFixEngine.diff |

**结论**: 核心诊断能力已具备，但"给出修改源码方案"这一步还没完成。需要补 CodeFixEngine 和 MF4 Parser。

## 五、鲁棒性提升建议

### 短期 (1-2 周)

1. **CodeFixEngine 安全审查**: 使用 `embedded-c-runtime-safety` skill 对生成的 diff 做自动化安全检查
2. **LLM 失败降级**: 当 LLM 调用失败时，有明确的 fallback 策略而非静默跳过
3. **ContextBudget 监控**: 记录实际截断量，当截断超过 10% 时告警

### 中期 (2-4 周)

4. **信号映射补全**: 补全 rteLite_PriCan.h 的 CodeGraph 边，让 240 个信号都有 READS/WRITES 关联
5. **BAG topic 自动发现**: 不硬编码 topic 路径，自动识别 wf 相关 topic
6. **诊断结果可验证**: 在诊断报告中标注"可复现的测试条件"，让用户能验证根因

### 长期 (1-3 月)

7. **多模态输入**: 支持视频/图片辅助诊断（如 CANoe 截图）
8. **批量诊断**: 对多个案例批量运行，生成趋势分析
9. **在线学习**: 用户反馈"诊断正确/错误"后自动优化记忆和 prompt

## 七、关键技术决策

### ADR-004: CodeFixEngine 使用 coder LLM 生成 diff

**背景**: 需要将诊断结论转化为可执行的代码修改方案。

**方案**:
1. 使用 `qwen3-coder:30b` (coder 路由) 生成代码修改
2. CodeGraph 提供精确代码位置
3. embedded-c-runtime-safety 做安全审查
4. 输出 unified diff 格式

**理由**:
- coder 模型专精代码生成
- CodeGraph 确保定位准确
- 安全审查防止引入新问题
- unified diff 是标准格式，可直接应用于源码

**风险**:
- LLM 可能生成不正确的 diff
- 安全审查可能遗漏边缘情况

**缓解**:
- diff 生成后做语法检查 (Python ast / lib2to3)
- 报告中标注置信度，低置信度时人工审核

### ADR-005: MF4 解析使用 mffparser

**背景**: 需要支持 MF4 测量数据格式。

**方案**: 使用 `mffparser` Python 库 (pip install mffparser)。

**理由**:
- ASAM MCDF 官方支持
- Python 原生，无需编译
- 社区维护活跃

**风险**:
- 安装可能失败 (依赖 C 库)
- 性能可能不足 (大型 MF4 文件)

**缓解**:
- 安装失败时 fallback 到 `mf4-converter` 命令行工具
- 流式读取，不一次性加载整个文件
