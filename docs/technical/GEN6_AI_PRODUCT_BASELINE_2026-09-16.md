## 1. 权威来源与适用范围

[访谈记录](GEN6_AI_PRODUCT_DISCOVERY_2026-09-16.md) 的 G6-R01～21 是用户确认需求；本文将其转为开发行为和验收标准。新增工程细化不冒充用户逐条确认。本文对三层交付、首期范围、授权修改、模式选择和性能口径的定义，优先于旧 PRD/实施计划中冲突的产品描述。旧 US/PC-AC 及其证据保留，不能凭新文档改写历史结果。

面向小范围算法工程师，以 Pi 对话为主要入口。输入单份 bag（不超过用户所述 10 GB）和问题描述，自动结合车型、COEM、录制软件版本与算法 branch/commit，完成场景与数据还原、根因调查，以及授权后的修改验证。

首期依赖工具组维护的 CR60 Light arbe，算法源码来自其子仓。链路从已处理点云/点迹开始，贯通 perception、situation、fct 和功能输出。不含 DSP/ADC，不建设团队平台；其他数据集回归作为后续接口。正常表现、性能取舍和代码缺陷都是合法调查结果，不要求每案修改代码。

首期同时交付 Pi 对话与实时浏览器工作页，共享同一案件状态；离线 HTML 为归档/分享。默认由工具管理独立分析会话，正式 GUI 行为验证采用显式模式。首期范围包括首次配置、稳定执行、取消恢复、安装与维护体验，不能把这些视为核心分析之外的无关事项。

## 2. 三层交付契约

| 层级 | 用户可见成果 | 完成条件 |
|---|---|---|
| L1 场景与现象 | 事件目录、问题时段、自车/目标场景、关键曲线、视频、输出变化及关联源码 | 解释观测到什么、依据什么，公开数据/时间/几何缺口；录制观察和回放复现分别标识 |
| L2 根因调查 | 代码—数据链路、GDB 关键变量、假设及反证、实验、原因解释与业务待裁决项 | 对调查范围给出证据支持的原因或明确未解决项；缺失链路不填造；需用户判断时资料足以支持该判断 |
| L3 修改验证 | 方案、影响范围、授权、diff、构建与回灌、前后比较、验证报告 | 预先定义的指标有结果；改动可追溯/可撤销；当前案例改善与未覆盖回归分开说明 |

三层共用一个调查上下文与证据账本，可逐步查看、追问、暂停和恢复。可以只完成用户要求的单层或单项查询，也可以从已有成果续作。它们不是固定工具调用序列。

“执行结束”“报告已生成”“因果调查完成”“业务判断完成”分别记录。证据不足的 partial 报告是有价值交付，但不算根因定位完成。已解释代码行为、等待用户作性能判断时，标为“技术解释完成，待工程判断”，不得擅自定性误报或非问题。

## 3. 用户旅程

1. 用户给 bag 和自然语言问题。Pi 从材料和已配置项目中解析身份，必要时只问影响结果的业务信息。
2. 自动核对录制版本映射、车型/COEM、源码、配置和 binary；展示简短任务摘要与已知缺口。缺少映射时可分析原始数据，但不能把当前任意分支当成录制版本。
3. 盘点四雷达中可识别的报警事件，按问题确定关注范围。事件很多时对相似场景分组，深入代表和差异事件，公开分组依据与覆盖范围，不把代表事件结论无条件扩展到全组。
4. 先提供 L1 有效成果，再自主补充查询、实验和 L2 报告。用户可用“看第二次报警”“关注右侧目标”等业务语言改变方向。
5. Pi 提出原因及最小区分实验。存在业务取舍时给出数据、代码和可能收益/代价，请用户裁决。
6. 需要修改时，先明确方案与验证标准，经授权执行 L3。仍可选择“不修改”，保留分析成果。
7. 返回统一报告和继续调查入口，后续追问复用有效结果；源码、配置、数据变化时复核依赖证据。

缺少报警时仍可调查漏报：从问题描述、视频或数据中的场景定位候选窗口，不把“没有报警事件”当任务结束。无法区分多个业务候选时给可理解的时间/场景摘要供选择，不让用户猜 frameID、PID 或 GDB 表达式。

## 4. Pi、原子工具与 arbe 的职责

| 责任方 | 应负责 | 边界 |
|---|---|---|
| Pi | 理解问题、选择工具和窗口、提出假设、规划实验、综合解释、与用户沟通 | 不自行编造数据值，不绕过授权和证据校验 |
| 原子工具 | 确定性解析/索引/查询、执行计划、编译/回放/GDB、状态与证据输出 | 预先实现并通过 Pi 注册；根因不由条件计数或硬编码规则决定 |
| 执行控制 | 权限范围、超时/取消、环境互斥、运行生命周期和资源清理 | 只管理执行，不建设第二个 AI 总编排器 |
| arbe adapter/provider | 复用工具组的播放、算法执行、调试等能力 | 算法仍由原代码执行；不在 Python 内另写一份感知或功能算法 |
| 报告 | 将同一调查状态与证据投影为可视化和文字 | 不在展示层重新推断事实或形成平行状态树 |

能力应覆盖：材料/身份解析、事件盘点、数据与视频窗口读取、源码检索、仿真规划与执行、GDB 规划与采集、证据查询、报告、补丁准备/应用和验证比较。先复用现有 BaseTool/BaseModule/catalog/registerTool，缺项经核查再实现，不为每个内部函数都新增工具。

每个工具具有明确输入/输出、单一有界责任、schema、ModuleResult、状态及错误语义、来源、耗时、输出大小与副作用声明。大数据返回摘要和 artifact 引用，通过有界查询读取，不把完整 bag、视频或代码库塞入模型上下文。长任务可查询/取消/恢复，副作用重试必须识别已有执行，避免重复启动。

## 5. 仿真与调试契约

- Pi 可自主选择目标级或点云仿真，并在既有授权范围内升级或比较；实际参数、资源或写入范围扩大时重新确认。
- `HILMODEL` 数值与语义来自当前源码和有效构建配置，不从旧文档固化。目标级跳过 perception，点云模式须有实际阶段执行证据才可声称重算。
- 每次实验绑定 bag、录制版本、算法源码含 dirty 内容、COEM、配置、binary、arbe 工作区、雷达源与执行 session。
- 复现录制版本与试验修改版本分别保存，不能用修复版行为解释原始版本的真实运行事实。
- 窗口包含必要历史和预热；预热长度依当前状态算法和实测确定，不统一写死帧数。保留 reset、实际处理范围、完成确认、丢帧与清理结果。
- GDB 字段保留真实作用域、变量、采集时刻和绑定。optimized_out、缺符号、断点未命中、源码/binary 不一致明确显示，不能拿默认值或邻帧补齐。
- GDB 或调试构建可能改变时序，必须记录构建及观测方式差异；不能把有侵入采集直接当作原环境性能证明。
- 首先比较基线回放与录制现象；复现不一致时调查配置、注入、初始化和环境差异，不能把偏差记为修复收益。

## 6. 数据与可视化可信度

所有消费证据保留 data/source/config/binary/session identity、原始字段 token、单位/缩放、枚举与有效性、变换及来源。录制、回放、GDB、确定性推导、AI inference 分层显示。未知值不是零、条件不可求值不是失败；恒定信号可触发质量检查，但仅“恒定”不能自动证明无效。

多雷达与对象关联必须有明确身份、帧域和映射依据。跨雷达同 ID、ID 复用、相近时间不能证明同一对象。坐标保留原点、轴向、角度、单位、传感器安装和变换来源；显示派生值时保留计算依据与原始值。

报告采用以下结构：

1. 用户问题、输入与版本摘要、当前层级、完成/未完成范围。
2. 全局事件目录，区分已盘点、已深查、待查与不可解析；支持按雷达、功能、时间定位。
3. 选中事件的场景播放、轨迹、关键属性、报警时间线、同步曲线和视频；联动同一明确时间/帧选择。
4. 点云→聚类/跟踪→目标→situation→fct→输出的代码—数据关联；未覆盖阶段显式缺口，不能用一张箭头图冒充全链路证据。
5. 现象阐述、分析、原因及反证、工程待裁决项和下一步。
6. 授权修改和验证对比，附可展开的来源、原始数值与产物。

尺寸、方向和形状以可证明数据/源码定义绘制；缺失时退化为明确的点/轨迹，不绘制伪实测包围框。雷达估计量也不等同物理真值。视频须保存对齐依据和误差/未知状态，不能靠近时间画面证明同帧对象身份。无视频仍可生成雷达重建场景。

## 7. 授权与低负担交互

设计采用任务范围授权：只读分析自主执行；仿真调试及修改验证分别明确目标工作区、动作范围、修改边界与预算。展示用户能判断的方案，不要求用户审阅每条命令。

同范围内复用有效授权；身份或方案改变时判断是否超出范围。对已授权动作不因缺少某个内部 approved 字段重复提问，也不能仅相信模型填入 approved。授权由可信执行边界记录并校验，范围扩大/预算超出/影响现有人工会话时再询问。

默认隔离修改与运行，保护用户 dirty 工作区和正在使用的 arbe/GDB 会话。停止只针对本工具可证明拥有的进程。提交、push、merge、发布不是修改验证的隐含授权。

只在业务歧义、授权或确实无法自动获得的关键输入处打断。模型失败、工具错误以业务语言解释影响，详细技术错误留在可展开证据中。中途成果和进度应可见，避免持续噪声；更改关注点不无故重跑全部数据。

## 8. 修改验证与工程裁决

修改前形成验证计划：现象、预期改变、源码/参数范围、基线版本、同 bag 的问题窗口和相关对照窗口、指标/阈值来源、通过/失败/不可判断条件。用户可修订方案；标准变化必须记录，不能看到改后结果再偷偷放宽标准。

AI 可依据源码和已知约束提出指标，性能收益与代价由用户裁决。需求不足时不臆造“允许误报率”等阈值。构建成功仅证明构建，原事件报警消失也不足以单独证明修复正确；须检查是否通过禁用功能、丢目标或改变输入造成。

首期只要求当前问题数据验证与可获得的同 bag 相关窗口比较；未来跨数据回归复用同一验证计划/结果契约。报告提供 diff、实际构建与运行结果、输入一致性、前后指标、未改善/新异常、未覆盖范围及恢复方式。

## 9. 性能与完成口径

用户目标：数据可访问、对应版本仿真环境就绪时，单 bag（不超过用户所述 10 GB）十分钟内完成请求范围内 L1/L2 报告，含必要回放/GDB。首次环境准备、版本切换编译和授权后的 L3 分别计时，并保留端到端总耗时。

工程计时方案：`T_total` 从用户提交请求到产物可查看；`T_prepare` 为一次性输入/环境准备；`T_analysis_wall` 从确认就绪并进入分析到 L1/L2 报告可查看；`T_user_wait` 单列；`T_L3` 单列。不得通过延后“分析开始”把普通解析、索引、hash、模型排队或报告渲染偷偷计入准备。已有前提满足时这些均属于分析耗时；分析中额外编译/模式切换不能自动移出十分钟预算。

主动分析耗时可另报扣除明确用户等待的值，但同时公布未扣除墙钟时间。不同模式、冷/热缓存、数据大小/时长、视频/事件数、机器/模型和网络条件分别记录，不承诺只靠 10 GB 上限即可保证任意数据达标。

优化优先级：一次索引复用、问题相关有界窗口、有效缓存、减少重复回放/模型输入、按需 GDB。缓存必须匹配当前签名；不能省掉预热或必要字段换速度。

十分钟内未查明则交付已证实信息和续作方案，标明 partial/待裁决/超时原因。降级是兜底，不计为完成目标通过。性能实测同时报告正确率/完成率及 p50/p95/最大值，不用平均时间掩盖失败案例。

## 10. 失败恢复与知识

| 情况 | 期望行为 |
|---|---|
| 版本、COEM、布局或 binary 冲突 | 保留原始数据分析，阻止依赖冲突证据的执行和结论；说明影响 |
| 数据损坏、字段缺失或视频不可用 | 交付可用部分、记录缺口和覆盖，不补默认真值 |
| GDB 不可获取或环境不可用 | 继续静态/公开证据调查，给实验缺口，保持 partial |
| 超时/中断/模型失败 | 保存已有产物；有界重试；恢复前复核身份，不重复已成功副作用 |
| 多来源矛盾或未复现 | 保留双方证据并优先调查差异，禁止选择有利结果拼接 |

同一调查可续作；历史知识按 variant/customer/branch 和 freshness 隔离。Auto Dream 仅发布当前成功 scope；不新鲜知识不得进入 prompt，历史案例不能升级为当次 observed。用户判断保留为带来源反馈，不自动变成跨项目事实。

## 12. 省心体验与代码变量落地（2026-09-16 补充设计）

### 12.1 产品成功标准

用户要求自主、稳定、低心智负担，明确痛点是分析文字未对应代码变量，仍需重新深入理解才知道如何修改。产品必须减少工程师的重复定位、数据换算、上下文切换和证据核对时间。报告篇幅、工具调用数量和 AI 输出速度不等于价值。

用户进一步澄清：代码变量只是示例，整个项目方方面面均需降低负担。因此第 12 节只是完整体验中的一个切片，不能以做好代码面板代替首次上手、输入、环境、调度、等待、失败恢复、修改验证和维护设计；完整约束见体验文档 UX01～11。

以下是针对该痛点的设计方案，不代表已实现，也不是新一次远端执行授权。

### 12.2 每项可行动发现的最低信息

默认按“现象→关键代码判断→实际输入与状态→来源→影响→下一步”呈现。标题用业务语言，旁边保留真实变量 token；不能用“风险值”“置信度”等泛称替代代码字段。

一项用于支持修改的发现须关联：

- 当前 source snapshot 的文件、函数、真实表达式与可打开代码片段；行号仅作辅助，源码变化后重新解析。
- 同一事件/雷达/对象/帧或明确时间序列下的实际值、类型、单位、有效性、采集位置与来源。列出条件所需操作数和实际配置阈值。
- 数据字段到代码变量之间的解码、缩放、坐标变换、索引和拷贝链。不能仅凭名称相似绑定，也不能把函数入口值当成后续更新后的值。
- 关键状态的初始化、写入/更新、分支、跨帧累计与消费位置；复杂表达式、别名或间接调用缺证据时明确缺口，不伪造完整链路。
- 当前代码行为为何导致输出，以及最小待验证因果关系。条件满足是行为证据，单凭满足不能确认根因。
- 可修改候选的准确位置、预期影响、依赖和副作用；上游输入错误不应默认通过放宽下游阈值掩盖。

证据类型区分 observed/derived/hypothesis；“按源码计算应为”不能显示成“GDB 实际为”。无法取得的变量显示缺失原因和已经尝试的采集，系统在授权与预算内继续补证，不能让用户从猜测中自行还原映射。

### 12.3 默认工作页

保留 Pi 对话入口，复用既有报告/Workbench 作为同一调查状态的视图，不建设平行任务系统。以下为信息结构，具体版式待真实任务可用性验证：

1. **任务摘要**：问题、项目/车型/版本、当前成果、是否需要用户决定；执行日志默认收起。
2. **关注事件**：四雷达事件总览及已分析覆盖；自动聚焦与问题最相关事件，允许一句话改焦点。
3. **场景与证据主区**：视频/俯视图、时间线和少量关键曲线共享选择；点击事件、目标或曲线不丢失当前上下文。
4. **代码解释区**：当前最重要发现直接并列显示代码片段和变量实际值；可展开上游赋值、历史变化及后续消费者。无需先读完全文才能看到源码。
5. **下一步决定**：明确推荐动作、原因、影响和仍未知的内容，例如继续补证、判断是否符合期望、审阅修改方案、授权验证；按任务状态出现，不同时堆出所有能力按钮。

默认先回答“发生了什么、代码为什么这样执行、还缺什么、现在需要我决定什么”。详细证据按需展开；可导出完整报告，但长篇分析不作为主交互。每次追问保留选中事件/目标/时间/代码位置；新结论替换旧结论时展示变更原因，旧证据保留。

### 12.4 减少用户决策而保持自主

系统自主完成版本查找、信号/代码映射、窗口选择、GDB 表达式生成、实验准备、失败重试和结果整理。工具不可用时先尝试有依据的替代证据，保持可信度标签；无法恢复再给具体缺口和最小用户动作，不倾倒工具报错。

提问应附场景与代码事实、选项影响及系统建议；不问“下一步查什么变量”。业务判断示例形式为“已确认当前逻辑在此场景产生该输出；是否接受这种行为”，而不是要求用户重新分析整条链路。模式自动升级仍遵守授权与预算。

修改方案与验证使用同一组关键变量、条件和事件前后对照，让用户看到改动改变了哪个值/状态/分支、原问题为何改善，以及同 bag 相关行为是否变化。证据不足时不生成看似精确的改代码建议。

### 12.5 可用性与价值验证

以真实工程师完成相同案例的过程验收：是否能直接判断结论依据、找到需修改或不应修改的位置、审阅验证结果。记录首次有效信息时间、到业务决定时间、人工搜索/换算/切换次数、提问数量、返工和理解错误；和原手工 arbe 流程比较。具体改善阈值先测基线再制定，不能自报“更省心”。

至少覆盖：找到代码缺陷、性能取舍但不改代码、变量不可获取、源版本变化、多雷达事件切换。即使分析耗时达标，用户仍须从头找变量/重新拼接证据才可判断，则 G6-AC12/13 不通过。
