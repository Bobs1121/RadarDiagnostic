# 诊断管线编排器 — Orchestrator

## 职责

Orchestrator 是整个诊断系统的中央调度器，负责按顺序执行 15+ 个分析步骤，将各阶段的产出组装成统一上下文，最后喂给 Expert Panel 做根因诊断。

它不是 AI 模块，而是**纯规则编排器**：控制执行流、传递数据、管理错误边界。

## 类定义

```python
class Orchestrator:
    def __init__(self, config: dict, router: ModelRouter,
                 project_root: Path, on_status: Optional[Callable]):
        self.config = config
        self.router = router          # AI 模型路由器
        self.project_root = project_root
        self.config_path = project_root / "config.yaml"
        self.project_config = _load_project_config(self.config_path)
        self.memory = Memory(project_root)
        self.on_status = on_status
        self._last_tpe_result = None  # TPE 结果缓存，下游 Visualizer 用
```

## 执行入口 — `run_diagnosis()`

```python
def run_diagnosis(self, case_dir: Path, problem: str, expected: str) -> Path:
    """
    完整诊断管线入口。
    
    Args:
        case_dir:  案例目录，包含 .bag + .blf 文件
        problem:   用户描述的问题（如 "RCTA 没有触发"）
        expected:  用户期望的行为（如 "有目标进入时应触发"）
    
    Returns:
        报告 Markdown 文件的绝对路径
    """
```

### Phase 0 — 前置条件检查

```python
self._ensure_source_docs(status)
```

扫描 `source_docs/` 目录，确保基础文件存在。如果 `source_docs/` 不存在（首次运行），自动触发初始化流程，调用 `SourceDocGenerator` 生成：
- `{FUNC}.md` (x8 功能文档)
- `signal_mapping.json`
- `output_mapping.json`
- `code_patterns.json`
- `parameters.json`

### Phase 1 — 问题理解

```python
session_id = self.memory.create_session(case_dir.name, problem, expected)
func_info = self._understand_problem(problem, expected, case_dir)
func_name = func_info.get("function", "UNKNOWN")
```

调用远端 AI 模型（`ai_complex` 路由），让模型读取问题描述后判断：
1. 涉及哪个 ADAS 功能（BSD / LCA / DOW / RCW / RCTA / RCTB / FCTA / FCTB）
2. 问题属于哪种故障类型（FP / FN / DELAY / STATE / OTHER）
3. 关键信息提取

**输出**: `func_info` dict，包含 `function`, `fail_type`, `description` 等字段。

### Phase 1.5 — 任务分类

```python
classifier = ProblemClassifier(router=self.router)
classification = classifier.classify(
    problem=problem,
    expected=expected,
    memory_hint=self.memory.build_context_for_diagnosis(func_name, problem, case_dir),
)
task_type = classification.task_type  # "diagnose" | "tune" | "verify" | "query"
```

使用 `ProblemClassifier`（见文档 04）对任务进行分类。分类结果决定后续管线行为：
- `diagnose`: 走完整 15 步管线
- `tune` / `verify`: 额外执行参数敏感性分析 + what-if 模拟
- `query`: 走轻量查询管线，跳过 Expert Panel

### Phase 2 — 数据解析

```python
store, bag_meta, blf_meta, sync = self._parse_case_data(case_dir, status)
```

内部调用 `CaseLoader.load_case()`（见文档 03），产出：
- `store`: `FrameStore` 实例（SQLite 内存数据库）
- `bag_meta`: ROS Bag 元数据 dict
- `blf_meta`: CAN BLF 元数据 dict
- `sync`: 时间对齐结果

### Phase 2.5 — 测试窗口检测

```python
detector = TestWindowDetector()
speed_thresholds = self._collect_speed_thresholds(func_name)
windows = detector.detect(store, func_name, speed_thresholds=speed_thresholds)
```

调用 `TestWindowDetector`（见文档 03），基于 6 种事件类型自动检测测试活跃窗口。窗口用于后续所有分析的时间范围约束，避免将无关时段的数据纳入诊断。

如果未检测到窗口，则使用全量数据。

### Phase 3 — 帧级证据提取

```python
var_path = self.project_root / "source_docs" / "variables.json"
analyzer = FrameAnalyzer(self.router, var_path if var_path.exists() else None)
frame_analysis = self._run_frame_analysis_with(analyzer, store, func_name, func_info, status)

evidence = analyzer.extract_evidence(store, func_name, windows=windows or None)
```

`FrameAnalyzer`（见文档 05）在测试窗口内逐帧扫描，产出结构化证据：
- `KEY_FACTS`: 关键事实摘要
- `timeline`: 事件时间线
- `state_transitions`: 状态跳变列表
- `warning_states`: 警告状态统计
- `ego_stats`: 自车统计
- `radar_objects_warned`: 触发警告的目标列表

### Phase 3.5 — 条件提取

```python
cond_extractor = ConditionExtractor(self.router, self.project_root, self.config)
conditions = cond_extractor.extract(func_name)
conditions_text = format_conditions(conditions)
```

从源码中提取 ADAS 功能的激活/取消/退出条件，输出结构化 JSON。使用 Hash 缓存机制，源码未变更时直接读取缓存。

### Phase 3.55 — TPE 时序模式引擎

```python
tpe_text, tpe_report = self._run_tpe(store, evidence, func_name, windows, status)
if tpe_report:
    FrameAnalyzer.append_tpe_block(evidence, tpe_text, tpe_report)
```

核心分析方法。详见文档 **08-TPE.md**。

### Phase 3.56 — 数值常量表

```python
constants_section = self.memory.render_constants_for_context(func_name, max_chars=2000)
```

从 AutoDream 学习到的全局数值常量（自车宽度、ROI 边界等）注入到专家上下文。如果尚未学习过，显示友好占位文本，明确告诉专家"阈值未知，不要猜"。

### Phase 3.57 — 动态变量探测

```python
probe_cfg = self.config.get("ai", {}).get("variable_probe", {}) or {}
probe_enabled = probe_cfg.get("enabled", True)

if probe_enabled and store is not None:
    planner = VariableQueryPlanner(self.router, self.memory, self.project_root)
    probe_plans = planner.plan(
        problem=problem, expected=expected, func_name=func_name,
        fail_type=func_info.get("fail_type", "OTHER"),
        focus_params=list(classification.focus_parameters or []),
        store=store,
        max_queries=int(probe_cfg.get("max_queries", 6)),
    )
    probe = DataProbe(store, windows=windows or [])
    for qp in probe_plans:
        probe_results.append(probe.query(**qp.to_query_args()))
```

AI 根据问题 + L6 代码知识，动态规划最多 6 条 DataProbe 查询，然后执行并格式化结果。详见文档 **06-动态变量探测.md**。

### Phase 3.6 — 外部抑制信号检查

```python
suppression_signals = conditions.get("external_suppression", [])
if suppression_signals and store.get_can_ids():
    suppression_text = self._check_suppression_signals(
        store, suppression_signals, windows, func_name, status,
    )
```

从条件提取结果中获取外部抑制信号列表，逐个在 CAN 数据中查找并验证。使用 `signal_mapping.json` 做内部变量到 CAN 信号名的映射，支持阈值判断和语义降级查找。

### Phase 3.7 — 输出信号分析

```python
output_signal_text = self._analyze_output_signals(store, func_name, windows, status)
```

从 `output_mapping.json` 中获取该功能的输出信号列表（制动请求 / 警告标志 / TTC 等），在 BLF 中提取实际 CAN 值，计算激活段、跳变次数、统计量。

### Phase 3.8 — 阈值参考

```python
threshold_ref = self._load_threshold_reference(func_name)
```

从 `source_docs/{func}.md` 中读取权威阈值参考，上限 4000 chars。用于专家诊断时对照阈值。

### Phase 3.9 — 参数敏感性分析（仅 tune/verify）

```python
if task_type in ("tune", "verify"):
    param_report_obj = analyze_sensitivity(
        source_root=Path(self.config["paths"]["source_code"]),
        cache_dir=self.project_root / "source_docs",
        store=store, func_name=func_name,
        focus_categories=classification.focus_parameters or None,
    )
    proposals = self._parse_proposals(problem, expected, param_report_obj)
    whatif_entries = what_if(param_report_obj, proposals=proposals, store=store)
```

扫描源码中的阈值参数，对每个参数做敏感性分析（穿越次数、min |Δ|、超阈值帧数），然后对用户的调优建议做 what-if 模拟。

### Phase 4 — Expert Panel 诊断

```python
panel = ExpertPanel(self.router, self.config, self.project_root)
panel_result = panel.run_panel(
    problem=problem, expected=expected,
    func_name=func_name,
    data_summary=combined_data,
    memory_context=memory_context,
    fail_type=func_info.get("fail_type", "OTHER"),
    task_type=task_type,
)
diagnosis = panel_result.get("final_verdict", "Diagnosis failed.")
```

将所有证据片段组装到 `ContextBudget`（详见下文），喂给 5 专家 3 轮研讨。详见文档 **09-专家面板.md**。

### Phase 5 — 报告 + 记忆更新

```python
report_path = self._save_report(
    case_dir, diagnosis, problem, expected,
    func_name, bag_meta, blf_meta, windows,
    task_type=task_type, param_report_md=param_section_md, whatif_md=whatif_md,
)

expert_appendix_path = case_dir / "expert_opinions.md"
self._save_expert_appendix(expert_appendix_path, panel_result)

# HTML 可视化
viz = build_html_report(case_dir=case_dir, func_name=func_name, ...)

# 更新 L1-L6 记忆
self._update_memories(session_id, case_dir, func_name, func_info, diagnosis, problem)

# 完成会话
self.memory.complete_session(session_id, f"Report saved to {report_path}")
```

## ContextBudget — 上下文预算管理

这是 orchestrator 最核心的创新机制之一。

### 问题

Expert Panel 的 prompt 需要包含大量证据数据（关键事实、时间线、TPE 结果、条件表、阈值参考等），每个片段都可能接近几千字符。如果全部拼接，很容易超出模型上下文窗口或浪费 token。

### 解决方案：优先级预算系统

```python
budget = ContextBudget(total_chars=60_000)

budget.add("methodology",   methodology_block, priority=100, min_chars=400)
budget.add("key_facts",     f"## ★ 关键事实(必读) ★\n{key_facts}", priority=100, min_chars=2000)
budget.add("tpe",           tpe_section,       priority=95,  min_chars=2000)
budget.add("constants",     constants_section, priority=94,  min_chars=800)
budget.add("probe",         probe_section,     priority=93,  min_chars=1500)
budget.add("suppression",   suppression_section, priority=92, min_chars=1000)
budget.add("output",        output_section,    priority=90,  min_chars=1500)
budget.add("windows",       f"## ★ 测试窗口 ★\n{windows_text}", priority=90, min_chars=400)
budget.add("transitions",   f"## 状态跳变\n{transitions_text}", priority=85, min_chars=600)
budget.add("conditions",    f"## ★ 条件检查表 ★\n{conditions_text}", priority=80, min_chars=1500)
budget.add("threshold",     threshold_section, priority=75,  min_chars=1000)
budget.add("params",        params_section,    priority=70,  min_chars=1000)
budget.add("timeline",      f"## 数据时间线\n{timeline_text[:10000]}", priority=60, min_chars=2000)
budget.add("frame_anal",    f"## 帧分析\n{frame_analysis[:6000]}", priority=55, min_chars=1500)
budget.add("evidence",      f"## 数据取证\n{evidence_text}", priority=55, min_chars=3000)
budget.add("data_summary",  f"## 数据概览\n{data_summary[:5000]}", priority=40, min_chars=1000)

combined_data = budget.concat()
```

### ContextBudget 工作原理

1. 所有片段按 `priority` 降序排列
2. 如果所有片段总长度 <= `total_chars`，直接拼接返回
3. 如果超出预算：
   - **从高优先级到低优先级逐个保留**
   - 低优先级片段逐步截断，但每个片段至少保留 `min_chars`
   - 截断策略：优先保留 Markdown 标题和结构化内容，截断尾部细节
4. 最终保证 `combined_data` 不超过 60K 字符

### 优先级设计逻辑

| 优先级 | 内容 | 为什么重要 |
|--------|------|-----------|
| 100 | 分析方法论 + 关键事实 | 定义分析框架，事实不可丢失 |
| 95 | TPE 因果对齐 | 最高价值的诊断证据 |
| 94 | 数值常量 | 专家需要精确数值做判断 |
| 93 | 动态变量探测 | 针对性数据，不可用硬编码替代 |
| 92 | 抑制信号实测 | 常见根因，必须验证 |
| 90 | 输出信号 + 测试窗口 | 外部可观测证据 + 时间范围 |
| 85 | 状态跳变 | 中间层证据 |
| 80 | 条件检查表 | 代码条件对照 |
| 75 | 阈值参考 | 辅助参考 |
| 60-70 | 时间线/帧分析/参数 | 细节数据 |
| 40 | 数据概览 | 最低价值 |

## 错误处理策略

Orchestrator 采用 **fail-open** 策略：
- TPE 失败：返回空字符串和空 dict，不阻塞后续管线
- 变量探测失败：记录日志，跳过该步骤
- 参数分析失败：仅 tune/verify 模式下才执行，失败不阻断
- 可视化失败：记录日志，报告仍然生成
- 记忆更新失败：静默跳过（使用 `try/except: pass`）

**唯一不可失败的步骤**: 问题理解、数据解析、Expert Panel 诊断。

## 关键设计决策

### 为什么 TPE 放在 Phase 3.55（条件提取之后）？

TPE 需要 `evidence` 中的 `state_transitions` 作为输入，而 state_transitions 由 FrameAnalyzer 在 Phase 3 产出。同时 TPE 的结果需要被 Phase 4 的 Expert Panel 使用。因此位置固定在 3.5 和 3.6 之间。

### 为什么抑制信号检查依赖条件提取？

`suppression_signals` 来自 `conditions.get("external_suppression", [])`，这是 ConditionExtractor 从源码中提取的结构化数据。Phase 3.5 必须先产出这个字段，Phase 3.6 才能使用。

### 为什么 ContextBudget 放在 Phase 4 内部？

因为所有 Phase 3.x 的产出（TPE、抑制信号、输出信号、条件、阈值、参数）需要在 Phase 4 入口处统一组装。如果在更早阶段做预算裁剪，会丢失 Phase 3.x 之间共享的中间数据。

### _last_tpe_result 缓存的作用

TPE 运行耗时（正则扫描 + 时序分析），但 Visualizer 需要 `TPEResult` 中的 `TPEResultPattern` 列表来绘制图表。缓存避免重复执行，同时保持 `run_diagnosis()` 返回值简洁（仅报告路径）。
