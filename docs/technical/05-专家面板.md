# 专家面板 (Expert Panel) — 多专家辩论诊断系统

## 职责

Expert Panel 是 radarAnalyze 的诊断核心：将问题分解给 5 个专业领域的 AI 专家，经过 3 轮独立分析、交叉审查、收敛讨论，最终产出结构化诊断结论。

## 架构 — 三轮辩论机制

```
Round 1: 独立分析 (并行)
    │ 5 个专家各自接收结构化证据表，独立分析
    │
    ▼
Round 2: 交叉审查 + 主持人挑战
    │ 每个专家看到其他专家的分析，主持人提出矛盾点
    │
    ▼
Round 3: 收敛 → 最终裁决
    │ 主持人综合所有意见，沿因果链追溯根因
```

## 五大专家

### 1. 信号链路专家 (signal_chain)

- **领域**: CAN 信号 → 内部变量映射
- **源文件**: `RteComMapping.c/h`
- **任务**:
  1. 查看条件检查表涉及的 CAN 信号
  2. 在数据时间线中找这些信号的实际值
  3. 追溯链路: CAN 信号名 → RteComMapping 宏 → 内部变量 → 哪个条件用了它
  4. 逐条检查信号是否正常
- **规则**:
  - 所有 `*SwtReq` 类信号 → `b*Enable`
  - 外部系统标志 → `g_DTCCode.b*ActiveFlg`
  - 车型变体: `g_GWMSpecificVariant.bits`
  - 不得把其他功能的映射套用到当前功能

### 2. 算法逻辑专家 (algorithm)

- **领域**: `adasFunc.c` 报警条件与阈值
- **源文件**: `adasFunc.c/h`, `paraDefine.h`
- **任务**:
  1. 逐条比对激活条件和阈值
  2. 检查: 自车速度、目标速度、角度/距离/TTC
  3. SkipFlg 的 dynFlg 条件
  4. DetectFlg 的使能条件
- **关键**: 因果链追溯 — 条件不满足时，继续追溯:
  哪行代码做判断 → 依赖哪个变量 → 变量来自哪个 CAN 信号

### 3. 系统状态专家 (system_state)

- **领域**: 双状态机与功能使能
- **源文件**: `ASWIN_SystemState.c/h`
- **任务**:
  1. 读取状态机实际值分布
  2. 查看状态跳变
  3. 逐条检查进入 Active/Standby 的前置条件
  4. 哪个条件阻止了预期状态转移
- **双状态机**:
  - `adasFunc.c`: 感知侧写 `*SystemState`(基于速度/故障)
  - `ASWIN_SystemState.c`: 平台侧写同一 `*SystemState`(基于自检/使能/速度)
  - `AdasStateActive()`: Standby(2)→Active(3) 需要 adasWarning 非零
- **关键**: 区分观测层与代码层 — 雷达端的 enable=0 是结果不是原因

### 4. 感知与目标专家 (perception)

- **领域**: 目标属性与过滤
- **源文件**: `objAttribCal.c`, `track.c`, `postProcess.c`, `structDefine.h`
- **任务**:
  1. 读取目标属性 (vel_x, dist_x/y, ttc)
  2. 比对目标筛选条件
  3. 当 A 类目标触发但 B 类不触发时，比较数值差异
- **关键**:
  - `trc_N_vel_x` 单位 m/s，代码阈值 km/h (×3.6 换算)
  - `objAbsV = sqrt(velAbsX² + velAbsY²)`
  - `*_flag` 列为 int8 状态码/bitfield

### 5. 架构专家 (architecture)

- **领域**: 左右雷达与输出合并
- **源文件**: `ASWOUT_OutCalc.c`
- **任务**:
  1. 确认数据来源雷达
  2. 检查左右数据是否一致
  3. 仅在涉及左右差异或合并逻辑时深入分析

## 专家选择 — 基于问题类型

```python
_FAIL_TYPE_EXPERTS = {

```

根据 `fail_type` 选择子集专家，减少 LLM 调用成本。

## Moderator (主持人)

### 因果链五层模型

```
L4 外部表现:   告警未触发/误触发（用户看到的问题）
L3 雷达观测:   radar_objects 中的告警标志、ADAS 使能状态
L2.5 时序耦合: TPE 分析的行为模式（保持-释放/累积-清零/防抖/滞回）
L2 ECU 逻辑:   adasFunc.c 中的条件判断、状态机跳变
L1 信号输入:   CAN 信号值 → RteComMapping → 内部变量
```

### 主持规则

1. **L3 观测值是"结果"不是"原因"** — 必须追问"代码中哪里产生了这个状态"
2. **TPE 已触发模式必须反映在根因** — 如果 TPE 给出 `verdict=triggered`，根因必须包含：模式名 + 关键时刻 + 信号时长 + 副作用变量
3. **TPE 未触发模式是反向证据** — 不能把 `not_triggered` 的条件写为根因
4. 条件不满足时 → 追溯到 L2 代码 + L1 信号
5. 没有数据支撑的假设禁止输出

## Prompt 结构

### 第一轮: 独立分析

每个专家接收:
1. **条件检查表** — 该功能的所有激活条件
2. **数据时间线** — 窗口化数据摘要
3. **关键事实** — 从帧分析器提取的统计
4. **TPE 段** — 时序模式分析结果
5. **代码片段** — 该专家负责的源文件相关代码

### 第二轮: 交叉审查

每个专家接收:
1. 自己第一轮的分析
2. 其他所有专家的第一轮分析
3. 主持人挑战: "你的结论与其他专家矛盾，请重新审视"

### 第三轮: 收敛

主持人综合所有分析:
1. 确认 L4 现象
2. 在 L3 找观测证据
3. 读 TPE 判断 L2.5
4. 在 L2 追溯代码路径
5. 在 L1 找到触发源
6. 根因 = L1 信号 × L2.5 时序耦合 × L2 代码分支

## 性能优化

1. **专家子集选择**: 根据 fail_type 只调用相关专家
2. **并行执行**: 5 个专家使用 ThreadPoolExecutor 并行调用
3. **源文件缓存**: 代码片段在 `__init__` 时加载到 `_source_cache`
4. **Token 控制**: 使用 ContextBudget 管理上下文大小

## 错误处理

- 单个专家失败: 标记为空分析，不影响其他专家
- 所有专家失败: 返回空结果
- 主持人失败: 返回第一轮专家分析的汇总
