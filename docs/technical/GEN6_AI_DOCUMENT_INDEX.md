## 2. 文档优先级与事实类型

用户明确决策 > 当前套件的目标契约。归档资料仅为历史证据/线索；需继承的规则必须先提取到当前套件，不能从归档恢复第二套开发指令。实现事实看当前代码，运行事实看带身份和日期的运行证据，不能用设计文字替代。凡新旧冲突已列入现状文档裁决表。

- `U`：本轮用户确认；`D`：设计方案；`C`：本轮读取当前代码所得；`H`：历史文档/产物记录，本轮未复跑；`V`：本轮实际执行并核验的结果。
- 设计状态与实现状态分开。新增需求不会自动升级历史 accepted，也不会改写历史测试结论。
- 缺少环境或事实先自行只读探测；只有产品取舍、不可自行获得的业务信息或授权范围变化才立即问用户。

## 3. DDD 变更规程

需求 G6-R → 用户旅程 UX → 设计责任模块 M → 工作包 WP → 验收 G6-AC → 实现 revision 与证据，必须能双向追踪。

开发前：描述用户可见问题与预期行为、相关需求、设计/接口差异、依赖、验收和失败路径（DoR）。

开发中：若发现原设计不成立，先记录事实和影响，同步本文档套件；业务目标变化立即确认，常规实现选择自行完成。不得用新增文档绕开旧阻塞项。

完成时：提交 diff、相关测试、真实产品链路证据、用户体验验收及限制（DoD）。只通过 unit/contract 不得标记 real-replay、Pi-product 或 UX pass。字段/schema 变更同步 AGENTS 与生产/消费方。

维护原则：新增事实进入现状；新需求进入产品和访谈；决策进入系统/模块责任段；计划进入实施；运行结果进入验收证据。handoff 仅记录变化和链接，不成为第二份产品基线。

## 4.1 开发启动与检查

后续 goal 先读执行规范、Sprint、执行状态和 handoff，从 S0/T00 起核验现场，不根据文档标题猜完成度。当前 `goal_started=false`。

`python tools/check_ddd.py`：文档/任务/状态一致性检查，返回 0 不代表产品完成。

`python tools/release_gate.py --plan-only --json`：只检查发布准备度，未执行验证时保持 blocked；完整命令 `python tools/release_gate.py --json` 也必须有实际必需验证命令与各层证据才能通过。

## 5. 本轮明确裁决

- Pi 唯一 AI 基座；按需原子工具，固定诊断步骤只是历史 fallback。
- 默认独立分析会话；正式 arbe GUI/PID 会话是显式模式，不自动宣称 parity。
- 首期 Pi 对话＋实时浏览器工作页，共享 AnalysisRun；离线报告用于冻结归档。
- 单 bag ≤用户所述 10 GB；就绪环境下 L1/L2 目标 ≤600 秒；L3 另计。
- 全局事件盘点后按问题深入；单案例回归为首期范围，跨数据集回归预留。
- 少打断和自主恢复适用于全流程；可信证据、可行动结论和节省工程师时间同时验收。
