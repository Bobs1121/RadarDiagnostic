03数据解析层

parsers/ — 将原始数据转化为结构化 SQLite 查询表。

BagParser

ROS1 Bag 手工反序列化。4 种消息类型：wfAutosarData (36B/目标)、wfObjectMsg (185B/目标)、egoCarInfo (69 字段)、UInt8MultiArray。解码失败降级为 raw_hex。

BlfParser

使用 python-can 的 BLFReader 遍历 CAN 帧，可选 DBC 解码为信号字典。

DbcLoader

多 DBC 加载，cantools 解码。同 frame_id 先到者优先，冲突记录。

FrameStore

SQLite 内存数据库，5 张核心表：bag_frames / can_frames / radar_objects / radar_debug / warning_events。支持按时间窗口查询。

TimeSync

BAG（纳秒）与 BLF（Unix 秒）时间对齐，支持手动偏移或首帧自动对齐。

CaseLoader

一键加载：自动发现 .bag/.blf，串联所有解析器，产出统一 CaseLoadResult。

SQLite 表结构：bag_frames (ROS 消息)、can_frames (CAN 帧)、radar_objects (雷达目标 + 8 功能警告标志)、radar_debug (自车状态)、warning_events (预计算报警事件，按 500ms 间隙切分)

3 轮研讨流程

Round 1：独立分析

5 位专家并发分析相同数据（最多 5 线程）。基于结构化条件表 + 数据时间线 + 关键事实，输出独立意见。

Round 2：交叉审查

主持人阅读所有意见，针对矛盾点和证据不足处提出质疑。被质疑专家并发回应。

Round 3：收敛判决

主持人综合所有意见和回应，沿因果链五层模型追溯，输出最终判决（final_verdict）。

智能专家选择 (V3)

故障类型选择专家
FP（误报）信号链路 + 算法逻辑 + 感知
FN（漏报）算法逻辑 + 系统状态 + 感知
DELAY（延迟）算法逻辑 + 感知 + 架构
STATE（状态异常）系统状态 + 信号链路 + 算法逻辑
OTHER（其他）全部 5 位

因果链五层模型

主持人使用的追溯框架，确保根因不停在观测层：

L4 外部表现 — 告警未触发 / 误触发（用户看到的问题）
↓
L3 雷达观测 — radar_objects 中的告警标志、ADAS 使能状态
↓
L2.5 时序耦合 — 保持-释放 / 累积-清零 / 防抖 / 滞回等行为模式
↓
L2 ECU 逻辑 — adasFunc.c 中的条件判断、状态机跳变
↓
L1 信号输入 — CAN 信号值 -> RteComMapping -> 内部变量
根因 = L1 信号 x L2.5 时序耦合点 x L2 代码分支

08时序模式引擎 (TPE)

系统的核心创新 — 将代码中的行为模式与数据中的时序信号做因果对齐。

代码侧（正则）
→
CodePattern
hold-release / debounce ...
↓
CausalAligner
因果对齐
↑
TemporalAnalyzer
数据侧（时序特征）
←
FrameStore
CAN 信号时间线

4 类行为模式

Hold-Release

保持-释放计时器：计数器递增 + 清零条件。如 HoldRelease 在 bLCAEnable 翻转时清零。

Accumulate-Reset

累积-清零：连续计数满足阈值后触发，中断时归零。

Debounce

防抖：边沿检测 + 延迟确认，过滤瞬态抖动。

Hysteresis

滞回：不同上下阈值，防止阈值边缘震荡。

对齐裁决

裁决说明
triggered数据时序与代码模式匹配
not_triggered数据时序不匹配（反向证据）
insufficient_data数据不足以判断
unknown变量无法映射到 CAN 信号
