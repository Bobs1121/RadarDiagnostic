## 调优效果分析 (核心!)

### 1. 当前状态统计 (旧阈值 1.0s)

从数据时间线可见警告跳变特征：
```
窗口 1(t=1775970400.99s): warning_edge_on + off 几乎同时发生 → 单次脉冲
窗口 2(t=1775970413.08s): on+off 同时 → 单次脉冲  
窗口 3(t=1775970417.55s): on+off 同时 → 单次脉冲
窗口 4-15: 大量 warning_edge_on/off 成对出现,间隔极短 (<20ms)
```

**结论**: FCTB 警告呈现高频闪烁特征，说明：
- TTMX 在阈值边界附近波动 (可能在 0.95s~1.10s 之间震荡)
- 迟滞量仅 0.1s (fFctbObjDeWarningTTMXOffSet),不足以稳定状态

### 2. 参数调整后预测 (新阈值 1.5s)

| 指标 | 旧值 (1.0s) | 新值 (1.5s) | 预期变化 |
|------|-------------|-------------|----------|
| **警告触发门槛** | TTMX ≤ 1.0s | TTMX ≤ 1.5s | ⬇️ 更容易满足 (触发率**增加**) |
| **去警告迟滞** | TTMX > 1.1s | TTMX > 1.6s | ⬆️ 更难退出 (稳定性**提高**) |
| **裕度空间** | ~0.05s(临界) | ~0.5s(充足) | ⬆️ 抗抖动能力增强 |
| **误触发风险** | 高 (阈值过紧) | 低 (容错空间大) | ⬇️ |

**⚠️ 关键矛盾**: 用户期望"触发频率降低",但实际上**调大 TTMX 阈值会增加触发敏感度**!

正确理解应该是:
- **触发次数可能略微增加** (更多弱风险场景被识别)
- **但触发后的稳定性显著提高** (不容易在临界值来回跳变)
- **综合误触发感知的用户体验改善** (不再出现"闪警")

## architecture


**TPE 一致性**: 无独立 TPE 文件，基于测试窗口事件日志分析。
- **触发模式**: `warning_edge_on/off` 频繁成对出现（如窗口 2, 3, 6, 7, 8, 10, 14），部分同帧跳变（t=1775970413.08s on & off）。
- **副作用**: 单帧触发导致 `GetFctbBrakeValue` 中的 `active_side` 状态频繁复位，制动请求值（`CR_BrkgReqVal`）在 0ms~900ms 间波动。
- **相关性**: 阈值调整直接影响 `obj_flag` 边缘产生频率，进而通过合并逻辑影响输出稳定性。

**条件检查表**
| 条件 | 阈值/要求 | 数据实际值 | 满足？ | 对应 TPE 模式 |
|------|----------|-----------|------|--------------|
| **触发逻辑方向** | 增大 TTM 阈值 (1.0→1.5) → 触发更敏感 | `TTMX <= Threshold` | **否** (逻辑相反) | 用户预期：触发减少；实际架构逻辑：触发增多 |
| **雷达源主导性** | 双雷达对称/一致 | `radar=2`(FR) 触发占比 >90%，`radar=1`(FL) 偶发 | **不满足** | 窗口 1/2/3/6/7/8/10/13/14 均为 radar=2 |
| **边缘稳定性** | 警告保持时长 > 1 帧 | 大量 `on/off` 同帧或相邻帧（窗口 2/3/8/10/14） | **不满足** | 单帧脉冲导致合并逻辑 `active_side` 震荡 |
| **合并仲裁依赖** | `active_side` 稳定 | `GetFctbBrakeValue` 依赖 `last_left/right` 边沿检测 | **受影响** | FR 侧抖动直接驱动全局制动请求切换 |
| **迟滞设计** | `Warning` vs `DeWarning` 差值 | `Base`=1.0, `Offset`=0.1 (差值仅 0.1s) | **风险高** | 易受 TTM 计算噪声影响导致乒乓效应 |

**结论**: 将 `fFctbObjWarningBaseTTMX` 从 1.0 调至 1.5 **违背**“减少触发频率”的目标（架构上会扩大预警窗口），且当前主要不稳定性源于 **Front-Right (radar=2)** 的单帧抖动通过 `GetFctbBrakeValue` (ASWOUT_OutCalc.c) 合并逻辑放大了制动请求闪烁，而非阈值过大；建议优先增加 **去警告迟滞 (DeWarning Offset)** 或 **最小保持帧数过滤**。

**需确认**: 请算法专家提供当前录制中触发瞬间的 **实际 TTM 值分布**，确认 1.0s 附近是否存在密集的噪声带以验证是否需要调整迟滞而非基线阈值。

### 补充分析(R2)


1. **数据来源确认**: 测试窗口内报警主要源自 **Front-Right (radar=2)**，占比 >90%，左侧 (radar=1) 仅偶发。左右数据源在场景分布上呈显著不对称，非同步触发。

2. **合并仲裁逻辑检查**: `ASWOUT_OutCalc.c` 中 `GetFctbBrakeValue` **不存在左右互斥复位机制**。左右警告标志位独立映射 (`bRightFctbWarning` 与 `GetFL_RSDS_BrkgReq`)，仲裁层仅通过比较边沿时间戳 (`timestamp`) 确定 `active_side` 以输出制动值，不会因一方触发而强制清零另一方标志位。

3. **同帧 On+Off 根因分析**: 
   - 非仲裁互斥导致，实为上游 `adasFunc.c` **迟滞带宽不足**。
   - 当前参数 `Base`=1.0s, `DeWarnOffset`=0.1s，目标 TTMX 在 **0.95s~1.10s** 临界区受噪声影响震荡。
   - 感知层标志位单帧翻转后，仲裁逻辑检测到下降沿 (`last=1 && current=0`) 即刻执行 `active_side=0` 复位，导致制动请求值在 **0ms~900ms** 间剧烈波动。

4. **结论**: 架构上无需增加仲裁互斥逻辑。应将 `fFctbObjWarningBaseTTMX` 调至 **1.5s**，利用增大的去报警门槛 (1.6s) 吸收 TTMX 波动，从源头消除抖动。

### 补充分析(R2)


**回答追问：BLF 中 TTMX 序列提取可行性与分布统计**

1.  **提取可行性修正**：
    根据「条件检查表」及信号链路分析，`radar_objects` 中**无直接 `trc_N_ttm_x` 字段**。此前分析中“需补充导出原始 TTMX"表述不严谨。实际上需通过 **`trc_N.rel_pos_x` (相对纵距)** 与 **`trc_N.rel_vel_x` (相对纵速)** 自行重构：
    $$ TTMX = \frac{|rel\_pos\_x|}{|rel\_vel\_x|} \quad (\text{仅当 } rel\_vel\_x < 0 \text{ 即靠近时}) $$
    若 BLF 缺少这两项运动学数据，则无法统计；若存在，可编写脚本还原报警时刻 (`warning_edge_on`) 的 TTMX 时序。

2.  **预期分布推断**：
    基于窗口 1-15 的抖动特征（同秒内 On/Off 频繁跳变），当前阈值 **1.0s** 处于目标实测 TTMX 波动核心区间。
    *   **[0.8, 1.0] 区间**：占比应较低，属高风险区，若触发则多为稳定报警。
    *   **[1.0, 1.5] 区间**：**预计为震荡主力区**（旧阈值下被判定为临界，导致标志位翻转）。旧参数下此区间目标虽接近但未稳定过阈，造成高频闪烁。
    *   **[1.5, 2.0] 区间**：当前极少触发，调优至 1.5s 后将覆盖此部分，提升预警冗余。

3.  **调优验证建议**：
    *   **步骤**：筛选 `warning_edge_on` 时刻，读取对应帧 `trc_0~3` 的 `pos_x/vel_x`，计算 TTMX 并落入上述三个桶。
    *   **预期效果**：若新阈值 (1.5s) 有效，**[1.0, 1.5] 区间的 TTMX 分布比例应显著增加**，且这些目标的报警持续时间应从 `<20ms` 脉冲变为 **>500ms** 稳定状态。
    *   **关键指标**：比较调整前后，**[0.95, 1.05] 窄带内的触发次数**。理论上该窄带抖动次数应随迟滞增加而减少（即使基线阈值放宽，稳定性也需提高）。

**结论**：无法直接读 TTMX，需计算；重点统计 [1.0, 1.5]s 区间的捕获率与报警稳定性变化。

### 补充分析(R2)


**回答：** 感知层警告标志会独立生成，但最终输出受 `ASWIN_SystemState` 全局状态严格门控。

1.  **时序差异**：窗口 1 显示 `warning_edge_on` 发生于 400.99s，而 `fctb_system_state` 在 401.23s 才从 6(Passive) 跳变至 2(Standby)，相差 **240ms**。证明 `adasFunc.c` 中的 TTMX 计算与阈值比较（<1.0s）不依赖全局状态即可执行。
2.  **输出逻辑**：根据 `ASWIN_SystemState.c` 源码，`AdasEnable()` 函数明确逻辑：`if ((fctbSystemState == 2) || (fctbSystemState ==3)) { bFCTBEnable = TRUE; } else { bFCTBEnable = FALSE; }`。`ASWOUT_OutCalc.c` 的输出级通常会校验 `bFCTBEnable`。因此，即使 400.99s 内部标志位已置位，由于此时 `fctbSystemState=6`，使能位为 **FALSE**，实际 CAN 输出与制动请求（CR_BrkgReq）会被阻断，不会对外下发。
3.  **根本原因**：车速在 **0.5km/h** 激活阈值附近震荡（实测 0.73~0.90km/h，多次跨越 0.5），导致感知侧频繁触发预警，而平台侧状态机需等待稳定后才允许功能输出。
4.  **修正结论**：此前分析认为“状态机阻止了触发”，准确应为“状态机阻止了输出”。调优方向维持原判断：增大 TTMX 阈值（1.0→1.5s）旨在解决感知层临界抖动，而非状态机门控问题。


## 主持人审查


### 矛盾点
- 用户期望与逻辑矛盾：用户期望阈值调大（1.0→1.5）能降低触发频率，但算法/信号/架构专家均指出 TTMX<=Threshold 的逻辑意味着调大阈值会扩大触发范围，理论触发率应增加或不变，而非减少。
- 稳定性归因分歧：算法/感知专家认为主因是 TTM 值在阈值临界区震荡（需调整迟滞），而系统状态专家指出部分报警发生于状态机进入 Standby 之前，暗示状态门控可能与警告逻辑解耦，导致阈值调整在特定时段失效。
- AEB 抑制逻辑歧义：信号专家指出 AEB 信号 99% 为 0（FALSE）对应“释放保持”，注释却称“非激活导致释放”，存在信号极性定义或注释描述不清的风险，影响对制动请求中断的根本原因判断。


### 遗漏
- 缺失 L1 关键数据：所有分析均无法直接获取 radar_objects 中的实际 TTMX 值分布，导致无法量化 1.0s 与 1.5s 阈值分别覆盖了多少真实风险场景，仅能推测 TTM 在 1.0s 附近波动。
- 缺失 L2.5 滤波细节：未明确 ASWOUT_OutCalc.c 中是否存在针对 obj_flag 边沿的最小持续帧数滤波（Debounce），当前观察到的单帧脉冲是否会被底层硬件/逻辑自动过滤，直接影响“调参必要性”的判断。
- 未验证状态机门控优先级：系统状态专家发现窗口 1 中警告边沿早于状态跳变 240ms，未确认此时输出层（Output Calc）是直接透传警告标志，还是受全局 fctbSystemState 门控，这决定了参数调整的生效边界。


### 关键争议
调优方向的有效性争议：将阈值从 1.0s 调至 1.5s 理论上会扩大预警范围（增加触发频次），这与用户‘减少触发’的主观期望相悖；核心在于区分用户真正想解决的是‘误报次数’还是‘闪烁频度’（后者可通过增大迟滞解决，前者需收紧阈值或优化滤波）。
